Selected work

Kinova Gen3 Lite manipulation suite

Physical demonstration, with related simulation and implementation prototypes

Engineering question
How do you turn motion-planning primitives into manipulation behaviors that can be inspected on hardware and in simulation?
My contribution
I built the original beer_pong ROS 2 package with single-throw and six-cup nodes, gripper control, MoveIt 2 commands, collision-scene objects, and checked-in joint-limit configuration.
Implemented approach
The suite combines MoveIt 2 motion commands and planning-scene setup with a Kortex gripper node. The throwing path triggers release from observed joint state; the related pick-and-place and writing prototypes use fixed task branches and fixed MAN stroke waypoints.
Evidence and current boundary
The physical throwing demo uses joint-state-triggered gripper release and open-loop targeting. The related repositories include captured Gazebo and RViz states and document current reproduction limits, not repeatability or hit-rate claims.

Technologies

  • ROS 2
  • MoveIt 2
  • C++
  • Kortex
  • RViz
  • Gazebo

NeuroBot

Implementation present, validation pending

Engineering question
Can a companion-robot perception pipeline degrade gracefully when one modality is noisy or unavailable?
My contribution
I implemented the face-processing and voice-session pipeline, modality adapters, AdaptiveGate, late fusion, fault-injection helpers, and a Jetson-oriented latency and power harness.
Implemented approach
The implementation keeps face processing local, adapts face, gesture, and audio outputs into a shared confidence representation, applies AdaptiveGate, and combines available modalities with late fusion. Voice sessions document Google speech-recognition and optional OpenAI service boundaries.
Evidence and current boundary
A compute-cost artifact records latency and board-power values across four Jetson power modes; the repository does not establish model accuracy, clinical inference, ROS 2 actuation, physiological sensor integration, or a validated multimodal improvement.

Voice sessions include documented cloud-service boundaries.

Technologies

  • Python
  • PyTorch
  • OpenCV
  • MediaPipe
  • NVIDIA Jetson

ArmBot

Robot-description concept

Engineering question
What has to be represented correctly before a custom arm can become a controllable robotics system?
My contribution
I created the six-joint Xacro and URDF description, seven STL meshes, launch definitions, and the CAD and historical RViz evidence in the repository.
Implemented approach
The implementation models the six-joint kinematic structure in Xacro and URDF, associates seven checked-in meshes with the links, and includes launch definitions for inspecting the description.
Evidence and current boundary
The repository demonstrates a robot-description concept and records a current clean-launch blocker. It does not present a demonstrated control system.

About

I work across the complete robotic system because most real failures do not respect discipline boundaries. A calibration offset can look like a planning problem, an electrical limitation can appear as unstable control, and a clean simulation can still hide a hardware integration issue. My approach is to make each boundary observable, document what the evidence proves, and iterate from the physical system back into the model.
